planes — visual identity

Master sheet and generation instructions · rough marker, not locked · July 24, 2026

The mark

Four grid planes crossing at a shared origin. Three are mutually orthogonal — the XY, XZ, and YZ coordinate planes. The fourth is oblique, sitting at roughly 54.7° to all three, cutting across the point where they meet.

The mark is 3D geometry. Every flat file is a projection of it at a chosen camera angle, not a drawing. There is no canonical 2D artwork to edit — there is a canonical geometry and a render script.

Known limit of the 2D stills. A static projection cannot assert orthogonality; that is a 3D fact and a flat image has no way to carry it. In a still, the four planes read as "four planes at various angles." The animated version is where the structural claim — three perpendicular, one crossing — is actually legible. Treat the stills as the compressed form.

Ink (axes, origin, wordmark) is the only thing that flips between backgrounds: #1A1A1A on light, #F2F2F2 on dark. Plane colors are identical in both.

Lockup — mark and wordmark together

Two orientations: horizontal for headers and wide layouts, vertical/squared for anywhere a compact square footprint is needed — app icons, social avatars, stacked cards. Both are emitted as files; what you see here is the same SVG inlined, so the sheet and the files cannot diverge. No tagline is locked; neither orientation includes one.

The wordmark is outlines, not live text — "Planes" set in Red Hat Display at weight 700 and converted to a path, so a lockup renders identically on a machine with no fonts installed.

Horizontal

Mark ink is matched to each ground (graphite on paper, light ink on graphite) rather than using the mark's own default light/dark ink — this lockup targets the UI palette specifically, not the mark's standalone light/dark backgrounds shown in Specimens below.

Vertical / squared

Mark centered above the wordmark, built for a square or near-square footprint. Uses the mark camera view rather than hero — its steeper angle reads better in a compact frame. Minimum recommended footprint is 160px square; below that, use the small view from Specimens instead of shrinking this lockup.

Same ink-matching rule as the horizontal lockup. Wordmark size is reduced relative to the horizontal lockup to keep the stack visually balanced at a square aspect rather than tall and narrow.

Which variant to use

VariantUse forNotes
heroSite headers, README, docs landing, slides Shallower angle; most legible depth.
markGeneral-purpose icon at 64px and above Full grid detail. Degrades below ~48px.
smallFavicon, avatar, anything under 48px No interior grid, heavier axes and origin.
animatedWeb hero, loading state, splash The only form that carries the full structural claim.
Verified at small sizes. Rasterized and inspected at 16, 24, 32, 48, and 64px. The mark variant turns to mud below 48px — interior grid lines are the first thing to die on downsampling. The small variant drops them entirely and thickens the ink; its origin dot and axis lines survive to 16px. At 16px it reads as a distinct shape rather than four legible planes, which is the honest floor for a four-plane crossing at that resolution.

Generating assets

render_logo.py is the source of truth. It has no dependencies and writes one SVG per view per ink color, plus this sheet.

python3 render_logo.py

Output goes to /mnt/user-data/outputs by default; override with the PLANES_OUT environment variable:

PLANES_OUT=./assets python3 render_logo.py

Files are named planes-{view}-on-{light|dark}.svg. This sheet is regenerated too — edit the template in the script, never the emitted HTML.

Adding a camera angle

Add an entry to VIEWS and re-run. Two SVGs appear for it automatically, and it joins the specimen rows above.

VIEWS = {
    "hero":  {"yaw": 32.0, "pitch": 24.0, "size": 280},
    "mark":  {"yaw": 38.0, "pitch": 28.0, "size": 280},
    "small": {"yaw": 38.0, "pitch": 28.0, "size": 240,
              "divisions": 0, "axis_width": 7.0, "origin_r": 11.0,
              "plane_stroke": 5.0, "fill_opacity": 0.42},
    "wide":  {"yaw": 55.0, "pitch": 15.0, "size": 280},
}

View parameters

KeyMeaningDefault
yawRotation about the vertical axis, degrees—
pitchTip toward the viewer, degrees—
sizeSVG viewBox edge length—
divisionsGrid cells per side; 0 or 1 omits interior lines6
axis_widthStroke width of the x/y/z lines2.0
origin_rRadius of the origin dot4.0
plane_strokeStroke width of each plane's border1.6
fill_opacityPlane fill opacity0.26

Avoid a near-isometric angle (yaw 45 / pitch 35.264). It makes the three coordinate planes symmetrical, which flattens the exact depth cue needed to tell them apart.

Changing the geometry

Edit PLANES. Each entry is two orthonormal basis vectors spanning the plane, plus a color. Keep u and v unit-length and perpendicular, or planes render sheared rather than square.

{"name": "record", "color": "#8B5CF6",
 "u": (0.7071, 0.0, -0.7071),
 "v": (0.4082, 0.8165, 0.4082)}

Global knobs: HALF (plane half-width), AXIS (axis half-length — how far the lines overhang the planes), DIVISIONS (default grid density).

Verifying geometry after an edit

Run this to confirm the basis vectors are still unit and perpendicular, and that the coordinate planes are still mutually orthogonal:

python3 -c "
import itertools, math
from render_logo import PLANES
def cross(a,b): return (a[1]*b[2]-a[2]*b[1], a[2]*b[0]-a[0]*b[2], a[0]*b[1]-a[1]*b[0])
def dot(a,b): return sum(x*y for x,y in zip(a,b))
def norm(a): return math.sqrt(dot(a,a))
n={}
for p in PLANES:
    c=cross(p['u'],p['v']); L=norm(c); n[p['name']]=tuple(v/L for v in c)
    print(p['name'], norm(p['u']), norm(p['v']), dot(p['u'],p['v']))
for a,b in itertools.combinations(n,2):
    ang=math.degrees(math.acos(max(-1,min(1,abs(dot(n[a],n[b]))))))
    print(a, 'vs', b, round(ang,2))
"

Expect lengths of 1.0, dot products of 0.0, 90.0° between each pair of coordinate planes, and ~54.74° between record and each of the other three.

Checking small sizes after an edit

pip install cairosvg pillow
python3 -c "
import cairosvg
from PIL import Image
sizes=[16,24,32,48,64]
for s in sizes:
    cairosvg.svg2png(url='planes-small-on-light.svg', write_to='/tmp/t%d.png' % s,
                     output_width=s, output_height=s, background_color='white')
imgs=[Image.open('/tmp/t%d.png' % s).convert('RGB') for s in sizes]
t=[im.resize((im.width*8,im.height*8), Image.NEAREST) for im in imgs]
W=sum(i.width for i in t)+16*(len(t)+1); H=max(i.height for i in t)+32
sheet=Image.new('RGB',(W,H),'#dddddd'); x=16
for i in t:
    sheet.paste(i,(x,16)); x+=i.width+16
sheet.save('/tmp/contact_sheet.png')
"

Then open /tmp/contact_sheet.png and look at it. Do not infer legibility from file size.
