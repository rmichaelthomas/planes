## 3. Method

**Calibration protocol, reused verbatim from `reports/REPORT_CALL_COST.md`
§1.2 and `scripts/measure_call_cost.py`/`.mjs`:** calibrate the loop
iteration count so one run takes ≥ 200ms; one further untimed warm-up pass
at `max(10% of N, 1000)` iterations; then 7 timed trials; report median and
minimum, never the mean; measure the control at the same calibrated
iteration count as the rung it will be subtracted from.

**Timer:** `time.perf_counter_ns()` in Python, `process.hrtime.bigint()` in
JavaScript — not `performance.now()`, matching `measure_call_cost`.

**Why nested `for each`, not recursion, for the ladder arms (§4):** identical
reasoning to `measure_call_cost` — Planes recursion has a ceiling far short
of the iteration counts a 200ms floor needs at sub-microsecond costs;
`for each` iterates with a native host-language loop, never touching that
ceiling; nesting two loops over the same modest list (`iter_L`, distinct
from the record width `W` or list length `L` under test) keeps source text
small while total iterations `N = iter_L²` scale quadratically. `iter_L` is
calibrated per rung exactly as `measure_call_cost` calibrates its own loop
length.

**Why these widths and lengths:** `WITH_WIDTHS = [4, 8, 16, 32, 64, 128]`
brackets the 4-field facet records and 7-field subject record Horizon §8
describes, at least up to a record wider than any single facet is likely to
need. `PLUS_LENGTHS = [64, 256, 1024, 4096, 16384]` brackets a session's
event log from a short warm-up to several hours at one event per second.

**Phase 2 (the world-shaped program) uses a different technique from the
ladder, deliberately.** The ladder holds parse cost outside the timed
region on purpose (the loop body executes many times inside one parse).
Phase 2 needs the OPPOSITE: Criterion A is a question about per-tick parse
cost, and today's actual per-tick architecture (`js/paint/loop.mjs`'s
`composePrelude`, confirmed in `REPORT_CALL_COST.md` §2, and Horizon §12's
own description of "the demonstration loop currently composes source
prelude text, parses and runs the graph, ... and repeats") re-parses on
every tick. So Phase 2 times the WHOLE program — `benchmarks/world_shape
.planes`'s shape, generated per `S` — through repeated calls to the
ordinary `Interpreter(host=TestHost()).run(src)` / `runProgram` entry
point, each one a fresh parse, calibrated the same way (a repetition count
`k` chosen to reach the 200ms floor, 10% warm-up, 7 trials, median/min).
Parse-only cost is measured the same way through `parser.parse()` /
`js/parser.mjs`'s `parse()` — the ordinary parse entry point, not an
interpreter internal — at the same `k`. `(b)` is never measured a second
time inside this program's own timing; it is looked up from the with/plus
arms already measured, applied to the actual widths (facet=4, tested
directly; subject=7, interpolated between the tested W=4/W=8 points;
world=3, extrapolated below W=4 from the fitted line) and to the actual
events-list length trajectory this program produces (0..31, averaged).

**Phase 3 (retention) runs the retention measurement as its own
subprocess**, both in Python and (as `node --expose-gc`) in JavaScript. In
first-cut, in-process measurements, Python's `ru_maxrss` — a process-wide
high-water mark — showed flat zero growth across all four checkpoints,
because the with/plus/cumulative/world phases that ran earlier in the same
process had already pushed the mark past anything the retention phase's own
600-tick, 64-subject run needed. That is a finding about the measurement,
not about retention, so it is corrected rather than reported: both
languages' retention phase is re-invoked as a fresh subprocess so the
memory reading reflects only its own footprint. `benchmarks/world_shape
.planes` and its own generator function (`build_world_src(64)` /
`buildWorldSrc(64)`) are checked byte-for-byte identical by
`test_update_cost.py`, so the file on disk and what the scripts measure
cannot silently drift apart.

**Machine:** Apple M1 Pro, Darwin 25.5.0 arm64. Python `3.14.6`. Node
`v22.23.1` — matching `REPORT_CALL_COST.md`'s machine, same repo, same

## 4. The criteria, quoted as written in the build prompt §1, before any figure below

> **Criterion A — the ordering claim.** Persistent-runtime work (parse
> elimination, module-graph caching, in-memory world values) takes priority
> over persistent data structures **if and only if** per-tick parse-and-load
> cost exceeds per-tick copy cost at the measured world shape.

> **Criterion B — the licence for structural sharing.** Persistent data
> structures are licensed as work **if and only if** copy cost in `with` and
> `plus` alone exceeds **2.0 ms per tick** — 20% of Horizon §16's 10 ms
> simulation gate — at the measured world shape, **with parse cost
> excluded**. Below 2.0 ms, the correct conclusion is that §59's naive
> implementation is adequate at this shape and the escape stays unexercised.

> **Criterion C — the scaling claim.** `with` cost is expected to scale
> linearly in record field count and `plus` cost linearly in list length. If
> measured cost is sublinear in either, the theory in §59 is wrong about the
> current implementation and the report says so before drawing any
> conclusion from Criteria A or B.

> Both thresholds and the linearity expectation are fixed here and may not
> be revised after the numbers land.

## 6. Verdicts

**Criterion A.** Per-tick parse-and-load cost is (a) in §5.3's table: 0.9%
to 6.7% of the tick in Python, 0.4% to 3.6% in JavaScript, at every
measured S, and it *shrinks* as S grows rather than approaching (b). It
never exceeds per-tick copy cost — (b) is 3-24× larger than (a) at every
measured point in both implementations. **Criterion A's condition is not
met: persistent-runtime work does not take priority over persistent data
structures on this basis, at the measured world shape.** This is a
narrower verdict than it might look: (a) and (b) together are a minority of
the tick — (c), the remainder (call dispatch and the per-tick list rebuild),
is 72-83% of the tick in both implementations, larger than (a) and (b)
combined at every measured S. Criterion A asks only about (a) vs. (b); it
says nothing about (c), and this report opens no question about it (§7).

**Criterion B.** Copy cost in `with` and `plus` alone, parse excluded, is
(b) in §5.3's table: 0.124-1.896 ms/tick in Python, 0.028-0.416 ms/tick in
JavaScript, across S=16..256. **None of the six measured points reaches the
2.0 ms threshold.** The closest is Python at S=256: 1.896 ms, **94.8% of
the threshold** — close enough to flag by name, per the build prompt's own
instruction to record proximity. Linearly extrapolating Python's two
largest measured points (S=64→256) past the tested range, (b) would cross
2.0 ms around S≈270 — a fact about where the fitted line points, stated as
an extrapolation beyond what was measured, not a finding at the measured
shape. **At every S actually measured, Criterion B's condition is not met:
persistent data structures are not licensed as work by this criterion, and
the correct conclusion per the build prompt is that §59's naive
implementation is adequate at this shape and the escape stays unexercised.**

**Criterion C.** Both arms fit a straight line with high confidence: the
`with` arm's isolated-copy-cost fit is R²=0.9670 (Python) and R²=0.9999
(JS) across W=4..128; the `plus` arm's fit is R²=0.9991 (Python) and
R²=0.9987 (JS) across L=64..16384. Every fitted slope is positive and
non-negligible (11.6-54.2 ns/field for `with`, 5.6-7.7 ns/element for
`plus`) — not the near-zero slope a sublinear (logarithmic, or effectively
constant) relationship would produce. **Measured cost is linear, not
sublinear, in both record field count and list length, in both
implementations. The theory in §59 is confirmed correct about the current
implementation: `with` and `plus` are O(n), consistent with a full copy on
every update.**

## 7. What this does not decide

A-Q3 — the optimiser's licence, what a persistent-data-structure
implementation would be permitted to change — **remains open.** This build
supplies its second precondition (v25.1 §375): the measurement §59 asked
for, now on record. It does not resolve A-Q3, does not implement a
persistent data structure, a HAMT, a trie, structural sharing of any kind,
parse elimination, module-graph caching, or an in-memory world runtime.

No new open question is opened by this build. Two observations are worth
naming as observations, not as questions:

- **(c), the remainder, dominates the tick (72-83%) at every measured
  world shape, in both implementations** — larger than (a) parse and (b)
  copy combined. Criterion A asked only about (a) vs. (b); this report does
  not extend the criterion to a claim about (c) it was not written to make.
- **The event log's `plus` cost, and the derivation graph's retained node
  count, both grow without bound over a session** (§5.2's cumulative
  measurement; §5.4's retention measurement) — exactly the behaviour §4.2
  and §6 of the build prompt anticipated, now measured rather than assumed,
  and consistent between Python and JavaScript (the `Deriv` count is exact
  agreement; the memory figures are the same order of magnitude).

The decision — whether either observation is worth acting on, and if so
how — is Rob's.
