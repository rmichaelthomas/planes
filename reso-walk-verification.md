## Findings closed during this build (surfaced by running the checks above, fixed in the same turn, per this project's own standing rule — not scope creep)

- **`test_gate.py`'s `test_the_landing_page_links_to_the_pages_it_ships_with` failed on the first full gate run**: `reso-walk.html` was deployed but `index.html` did not link to it — a pre-existing, repo-wide, non-negotiable rule (every shipped root page is linked from the front door), directly precedented by PR #95's own `index.html` edit when `horizon-crossing.html` replaced `a-crossing.html`. Added a showcase card. This IS an edit to a file outside the build prompt's own four-file list, but it is not a substrate edit under invariant 1's actual concern (the engine files) — it is a required, mechanical, precedented repo-hygiene fix, closed directly rather than deferred.
- **`scripts/ci.sh`'s own `set -e` truncated the gate at the test-suite step** on the first full run (because of the `index.html` finding above) — every later step (`node --test`, `ruff`, `mypy`, etc.) never ran at all on that pass, exactly the standing gotcha this project's own memory names. Fixed the real defect, then ran the remaining steps directly for genuine confidence, then re-ran the whole gate twice more end-to-end (clean, both times) rather than trusting a partial run.
- **`ruff` found 10 real violations in `test_reso_walk_in_planes.py`** (nine `E741` ambiguous-variable-name `l`, one `E501` line-too-long) — fixed directly.
- **`scripts/verify-reso-walk.mjs`, as the build prompt names it, cannot be committed**: this repo's own `test_gate.py` forbids a committed `scripts/verify_*`/`verify-*` file in any language/extension (the exact rule `crossing_port.test.mjs`'s own header documents, PR #94/#95). Graduated the verification logic directly into `js/test/reso_walk.test.mjs`, following that file's own precedent, rather than writing a script the gate would then reject.
- **A real visual-legibility bug, found by actually looking at the agent's own capture (§9.3), not just running assertions**: the fixture's first-pass dock strip (`[0.08, 0.80]`) reused the crossing's full Reso-to-Nkwo-Eriri channel width, but `pixi_performer.mjs`'s shared environment image only shows recognizable dock/market imagery in a narrow band near `x≈0.05–0.20` — the rest is open channel water (the disclosed rendering gap below, but a worse manifestation of it than expected). At the original `boy-start-x=0.62`, the resting camera framed the body floating in open water with no dock in view at all. Retuned the dock band, start position, step, and touch range to stay inside the image's own dock imagery (`paint/reso_walk.planes`'s own header documents the exact retune and why); updated every test assertion that depended on the old numbers; re-verified end to end (both suites, both implementations, fresh captures). Also caught and fixed in the same pass: the HUD's "the market answers" status was keyed off the one-tick-only `scene cue` value, which the 60ms poll could step over entirely (found live: a real touch registered, `market.state` correctly read `greeted`, and the HUD still read "Walking the dock."); re-keyed it off the persistent `market.state` instead.

## The disclosed rendering gap (not a defect this build introduced or could close)

`parseSceneIntent` (`js/scene/ir.mjs`) only ever reads `scene `/`audio ` lines — every `draw ...` line the fixture emits (reused crossing render vocabulary, plus the new walking-figure draw code, §3.5) is real and honest but has no live consumer on the engine path, exactly as `a_crossing.planes`'s own `draw` block already does not since `a-crossing.html`'s retirement (PR #95). `js/world/performers/pixi_performer.mjs` — a shared file, not in this build's file list, not touched — renders every scene subject other than its one hardcoded `hydrofoil` id as a generic colored, labeled circle badge, and never reads a subject's `state` field. So the boy renders as the same kind of badge every unstyled crossing subject (`kordas`, `clinic-beacon`, ...) already does — not a rendered walking figure — and the market's touched/greeted state is surfaced through the page's own HUD (reading `parseSceneIntent`'s output directly), not a Pixi-level visual change to its badge. **Surfaced to the architect before writing any code** (this session's own record): proceed within the current substrate, disclose plainly, versus a small additive `pixi_performer.mjs` extension. The architect chose to proceed within the current substrate. Movement, the eased camera, the traced position, and the touch interaction are all fully real underneath the badge — confirmed by every check above and by the capture frames, which show the badge correctly positioned against real, showcase-quality Reso dock imagery throughout.

## What this build did not do — held out by design (§1, §7 invariant 5)

Build-mode/world-authoring, the descend/perspective shift, role-constrained agency, world-traversal beyond one dock strip, a second interactable, dialogue, an art pass giving the boy or the market bespoke Pixi-level visuals. The boy is a body, not a role; the market responds, not as a role would.
